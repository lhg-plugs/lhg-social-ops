# lhg-so-review：数据复盘

> 目标：从数据里抠出"下周干什么"。
> 核心纪律：**复盘的终点是行动清单，不是数据陈列。**

## 1. 何时使用

- 每周/每月固定复盘（建议：周复盘 30 分钟，月复盘 2 小时）
- 数据突然爆了或崩了，紧急复盘找原因
- 跑 `/lhg-social-ops:review` 命令时，本 skill 是方法论底座

## 2. 输入与输出

- **输入**：`data/posts.json`（字段：id/平台/发布时间/文案/标签/播放/点赞/评论/转发/涨粉）+ 周期
- **输出**：`reviews/YYYY-MM-DD.md` 复盘报告 + 下周调整动作（回写日历）

## 3. 第一步：收数与验数

### 数据格式
```json
[
  {"id": "p001", "platform": "xhs", "published_at": "2026-10-05T20:00:00+08:00",
   "text": "…", "hashtags": ["财经", "财报"],
   "views": 12000, "likes": 340, "comments": 45, "shares": 60, "new_followers": 28}
]
```

### 验数（先验再算）
1. 关键指标缺失（无 views/播放）→ 标出来，不许拿残缺数据下确定性结论。
2. 数据量 < 5 篇 → 写"样本不足，暂不归因"，只做数据一览。
3. 疑似买量（播放高但互动率 < 0.5%）→ 标出来问用户，不许当正常数据用。

## 4. 第二步：跑确定性审计

```bash
python3 <插件目录>/scripts/audit/account_audit.py --target data/ --format text
```

机器先扫一遍：断更/刷屏/标签问题/违禁词/互动异常。人的归因建立在"运营动作先合规"的基础上——文案有违禁词，数据再好也是定时炸弹。

## 5. 第三步：四段式复盘报告

### 段 1：数据一览（只摆事实，不下结论）
- 总发布 n 篇，总播放/阅读 x，涨粉 y，取关 z（如有）
- 爆款 top 3（链接+核心数据）
- 环比上周：涨/跌 + 百分比

### 段 2：爆款归因（找共同点）
top 3 逐篇拆：选题/形式/发布时间/标题结构/开头方式，找**至少 2 个共同点**。
- ✅ "top 3 都是'拆一家公司'选题，且标题都是'数字+结论'结构"
- ❌ "内容质量高"（空话，删掉）
- 找不到共同点 → 写"样本不足，暂不归因"，不许硬编。

### 段 3：哑火诊断（每个一句话死因）
bottom 3 逐篇诊断，死因必须具体：
- ✅ "选题太泛（'聊聊经济'），人群对不上"
- ✅ "发布时间撞上热点大事件，被淹没"
- ❌ "内容不好"（空话，删掉）

### 段 4：下周调整（复盘的落点，没有这段等于没复盘）
- **加什么**（1-2 个）：爆款共同点的复制，如"加一期'拆一家公司'选题"
- **停什么**（1-2 个）：哑火死因的止损，如"停掉无数据支撑的宏观空谈"
- **试什么**（1 个）：新动作，如"试一篇问答形式"

## 6. 第四步：闭环（复盘不进日历 = 白做）

1. 下周日历按"加/停/试"重排（`calendar/` 更新）。
2. 定位卡要不要调？→ 只有当归因指向"人群/价值/差异化"本身时才调定位，执行问题不调定位。
3. 审计发现的合规问题（违禁词/刷屏）→ 进"运营红线清单"，下次发布前对照。

### 周复盘 30 分钟流程（SOP）

| 分钟 | 干什么 |
|---|---|
| 0-5 | 收数：posts.json 更新到最新，验数（缺指标/样本不足先标出来） |
| 5-10 | 跑审计脚本，看 blocker/warning，先处理合规问题 |
| 10-18 | 写数据一览 + 爆款归因（找 2 个共同点）+ 哑火诊断（一句话死因） |
| 18-25 | 定下周调整：加/停/试各写清楚 |
| 25-30 | 更新日历：把"加/停/试"排进下周；审计问题进红线清单 |

30 分钟掐表做，做不完说明数据没收齐（回去补数），不是复盘方法的问题。月复盘 2 小时 = 4 次周复盘串起来 + 定位卡要不要调的讨论。

### 归因 checklist（防拍脑袋）

下结论前逐条打勾：
- [ ] 样本 ≥ 5 篇吗？（不够 → 只陈列，不归因）
- [ ] 对比了"爆 vs 哑"的差异吗？（只看爆款不看哑火 = 幸存者偏差）
- [ ] 排除了发布时间/热点等外部因素吗？
- [ ] 结论能指导下周动作吗？（不能 → 这条归因没用，删掉）

归因是为了复制成功、止损失败。通不过 checklist 的归因，宁可写"暂不归因"，也不要给下周指一条错路。

## 7. 复盘报告模板

```markdown
# 复盘：<周期>（<日期>）
## 1. 数据一览
## 2. 爆款归因
## 3. 哑火诊断
## 4. 下周调整
- 加：
- 停：
- 试：
## 5. 审计结论
- blocker/warning/nit 数量与处理
## 6. 需人工确认
- <数据存疑/买量嫌疑/归因不确定，列出来问用户>
```

## 8. 反模式（不要这么做）

- ❌ 复盘只摆数据不下结论——那是报表，不是复盘
- ❌ 爆款归因写"运气好"——归因不到位，下周没法复制
- ❌ 哑火诊断写"内容不好"——空话，删掉
- ❌ 下周调整全是"继续加油"——必须有加/停/试
- ❌ 拿残缺数据下确定性结论——缺什么先说什么
- ❌ 复盘完不改日历——等于没复盘
- ❌ 执行问题调定位——定位是宪法，执行没做到位就改执行

## 9. 自检与反馈

每次执行完本 skill，做一次轻量自检：

1. 四段式齐了吗？→ 缺"下周调整"打回重写。
2. 爆款归因找到 2 个共同点了吗？→ 找不到就写"样本不足"。
3. 哑火死因具体吗？→ 空话删掉。
4. 复盘结论回写日历了吗？→ 没回写等于白做。

如发现本 skill 自身的方法论缺陷，按以下流程反馈：

- **标准冒烟用例**：用 10 篇样本数据走一遍本 skill，检查四段式是否齐、归因是否有共同点、调整是否有加/停/试。
- **一键提 issue**：确认问题后，以 `[QC] <一句话问题>` 为标题、正文写清"复现输入 → 错误输出 → 期望输出"，提交到 https://github.com/lhg-plugs/lhg-social-ops/issues。
